# Build plan — IT access requests

This plan implements [spec.md](spec.md) R-01–R-104. Only this Markdown file is written in the current task; all commands, paths, fixtures, tests, reports and implementation work below are future work. Existing starter tests are examples, not proof of any planned behavior. No live API call, code/test creation, dependency installation, commit or push is part of drafting this plan.

## Choices

| Choice | Decision and reason |
|---|---|
| Runtime | Python 3.12 on the supplied Linux environment (3.12.3 observed); standard-library argparse, sqlite3, urllib, hashlib and unittest plus jsonschema, pinned with its transitive dependencies in pyproject.toml/uv.lock, keep the runtime small and provide a concrete lockfile. |
| Interface | A CLI package named `it_access`; intake runs in the foreground while another invocation reads queue/pending/history from the same SQLite state, giving reviewers partial results without a web deployment. |
| Test command | After future `uv sync --locked`, run `env -u API_KEY .venv/bin/python -m unittest discover -s tests -v`; no test opens sockets or reads a real credential, and every provider/HTTP call is replaced by a fixture or injected transport. |
| Model provider call | A concrete OpenAI Chat Completions HTTP adapter via injected urllib transport; `provider=mock` is the default and test mode, `provider=openai` is explicit, endpoint/model/options are configuration, and the live-only credential supplier reads API_KEY. A schema-capable model ID must be explicitly configured and recorded; no model availability, live success or API-key access is assumed by this plan. |

These are implementation choices, not additional requirements. Design references checked during planning: [Python sqlite3 transactions](https://docs.python.org/3.12/library/sqlite3.html), [SQLite WAL constraints](https://sqlite.org/wal.html), [jsonschema validators](https://python-jsonschema.readthedocs.io/en/stable/validate/), [uv locking/sync](https://docs.astral.sh/uv/concepts/projects/sync/), [OpenAI Chat Completions response fields](https://developers.openai.com/api/reference/resources/chat), and [structured output/refusal handling](https://developers.openai.com/api/docs/guides/structured-outputs). The adapter will request a strict extraction schema, accept one completed non-refusal text choice, then independently parse/validate it; malformed envelopes, refusals and non-stop completion reasons fail explicitly. The planned production base URL is `https://api.openai.com/v1`; endpoint/model overrides are explicit settings, and no live access is implied. Future implementation must check the chosen model's supported request options and document one supported concrete model configuration using API documentation; this does not require a live call.

**Decision D-01 — user-resolved policy questions:** the user answered “Retain IT-014 dates and IT-006 read permission”. E-014 therefore retains both reversed explicit dates with a clarification issue, and E-006 retains the original read permission while the later admin command is preserved as override evidence. This resolves spec Q-34/Q-45 for the plan without editing the spec.

**Storage and operating choices:** support overlapping CLI processes on a single host using one local SQLite database, not a network-mounted database or active multi-host writers. Start with a shared limit of four concurrent model calls, a configurable request-rate budget coordinated in SQLite across same-host operators, 60-second transport timeout, and at most three attempts for declared transient failures with delayed backoff and a configured cap; lease renewal and expiry use a separately tested clock. These are tunable defaults to verify, not source-mandated numbers. WAL requires same-host cooperating processes; local-process concurrency and mock workloads do not demonstrate geographically distributed storage or live-provider throughput. Retain input bytes and attempt/result history without automatic pruning in the first implementation; credentials are never retained. External provider requests may repeat after a crash; fenced database publication prevents stale current results, not duplicate provider charges.

**Source and current-state choices:** use case-sensitive basenames from one nonrecursive intake directory and reject conflicting paths rather than merging them. Assign a monotonic per-document generation when a byte revision or relevant processing fingerprint is registered; “latest” means the latest registered generation, not exported_at or response completion time. Earlier completions become history. Immutable source bytes, configuration fingerprints, explicit attempt IDs, policy versions and extraction-parent references distinguish every result. Process-state pending/running/retry-wait is separate from policy review/error status; current queue shows the latest terminal attempt and explicitly labels an older result if newer work is still pending. Unchanged valid results are reused; failed work is not silently retried by a plain rerun. Explicit retry/resume uses retained snapshots/settings and can never overwrite a newer generation.

**Validation and reporting choices:** select Draft 2020-12 validation externally without editing snapshot.schema.json; enforce its existing keys/types/enums and decoded quote-substring checks. Use an internal typed findings representation derived from validation and the extraction's issues strings; the prompt/fixtures can adopt explicit issue prefixes such as `missing:<field>`, `conflict:<field>` and `override:<evidence>` as an implementation contract without adding extraction properties or routing on every nonempty issue. Override recognition depends on source evidence identified by the extractor plus the clear supplied override marker; fixture tests verify routing and prompt construction, not comprehensive live prompt-injection detection. Use strict JSON parsing and explicit errors rather than silent JSON/quote repairs. Canonical business-purpose text in the E table is an exact source excerpt chosen for a deterministic exact-match measurement, not a claim that the policy forbids all other faithful summaries. Score the twelve scalar extraction fields for all 21 accuracy cases, counting null equality as a match, case/whitespace/text differences as mismatches, and every missing/error document as twelve nonmatches; denominator=252. Report quote integrity, required issue coverage and owner/status/action separately; do not order-match prose arrays or invent a passing-score threshold. Baseline mock equality demonstrates the pipeline/comparator, not live model quality.

**Outputs and limits:** the submission intake workspace will contain the supplied 20 exports; the 21-case accuracy workspace adds the synthetic export separately. Default deliverables use mock response_source and include no earlier versions as current rows. Exact output counts and workspace separation are documented choices under Q-68. Provider settings and error-source attribution use an explicit string such as `openai:<requested-model-id>` or `mock`, plus separate requested/returned-model provenance; attempted provider identity is retained even if the request fails.

**Questions that still need a person:** the source does not define a full override detector, mixed/multiple-intent extraction, alternative correction phrases, impossible/partial dates, or unknown permission/environment concepts (Q-25/Q-30–Q-33/Q-36/Q-43/Q-44). This plan covers the stated rules and clear supplied cases, with ambiguous scalar facts left null and explained according to the policy; it does not silently add a general classifier or semantic repair rule. Before implementing assertions for those novel boundary cases, the operator/facilitator must answer them. The concrete model ID/allowed endpoint, actual multi-host deployment needs, accuracy-summary alternatives and final capture/Classroom acceptance details also remain to be confirmed in the relevant later step. They do not block the mock-first source-grounded build or authorize guessed company rules.

Do not deliberately break already working behavior to manufacture a red test; record if a new test already passes and add a genuinely missing acceptance boundary before claiming a step needs code.
